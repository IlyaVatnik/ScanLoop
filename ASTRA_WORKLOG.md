## 1. Транспорт: доказано исходниками

### 1.1. Конечная точка и открытие

- Hardware/ova5000.py:31–36: создаётся обычный IPv4 TCP-сокет socket(AF_INET, SOCK_STREAM), затем settimeout(2), затем connect((host, port)). Значение RESPONSE_TIMEOUT=2 задано в строке 13.
- Windows_GUI/MainWindow.py:591–593 передаёт только port=self.hardware_ports.LUNA. host остаётся значением 'localhost'. В исходной конфигурации Common/Hardware_ports.py:19 порт LUNA=1; это не доказательство фактического порта в пользовательском запуске. Значения могут быть заменены через set_attributes (строки 23–25), в том числе при загрузке параметров (MainWindow.py:1612–1622).
- Следовательно, штатный путь GUI подключается к TCP-службе на том же компьютере, а не к явно заданному IP прибора. [ГИПОТЕЗА] Этой службой является ПО Luna или посредник; его реальная роль, версия и связь с прибором пока не установлены.
- Раздельных таймаутов соединения, записи и чтения нет: один socket timeout 2 с остаётся установленным на дальнейшие операции. Это не общий предел длительности измерения. Разрешение имени и суммарная длительность множества операций этим значением не ограничены как единая транзакция.
- Нет setsockopt, SO_KEEPALIVE, настройки TCP_NODELAY, SO_RCVBUF/SO_SNDBUF, специального режима повторного подключения или проверки состояния сокета. ОС использует свои настройки; фактические размеры её буферов в этой фазе не измерялись.
- BUFSIZE=4096 (строка 15) — максимальный размер одного recv, а не размер всего ответа и не настройка буфера TCP.

### 1.2. Отправка и разделение ответов

- Hardware/ova5000.py:54–73: используется sock.send(str(cmd).encode()), а не sendall. Число отправленных байтов игнорируется. При частичной отправке остаток не досылается.
- Драйвер не добавляет к исходящим командам ни LF, ни CR, ни NUL. В показанных вызовах SCAN и SYST:RDY? терминаторов также нет. Допустимость такой передачи определяется протоколом сервера; сама по себе она ещё не доказывает нарушение спецификации Luna.
- recvall (47–52) читает блоки до тех пор, пока последний байт всего накопленного массива не равен 0, то есть NUL. Ожидания '\n' нет.
- Проверяется только arr[-1], а не позиция первого NUL. Если один recv принёс полный ответ плюс начало следующего, первый ответ отдельно не выделяется. Если пришло несколько ответов и последний заканчивается NUL, они возвращаются одной строкой. Очереди сообщений, сохранения хвоста после первого терминатора и сопоставления ответа запросу нет.
- arr — локальная переменная одного вызова; постоянного прикладного приёмного буфера нет. Нет очистки входного потока перед новой командой, ограничения длины сообщения или общего срока сборки ответа. arr += recv копирует накопленные байты при расширении.
- decode() выполняется после окончания чтения и по умолчанию ожидает UTF-8. Неподходящие байты дадут UnicodeDecodeError; специального восстановления нет.
- FETC:XAXI? и FETC:MEAS? разбираются посредством raw[:-2].split('\r') и преобразования в float64; последние два символа отбрасываются без проверки, затем отрезается по 10 отсчётов с краёв (96–100, 43). Это предположение драйвера о формате, не подтверждённая в этом куске спецификация прибора.

### 1.3. Ошибки и принцип «молчание означает успех»

| Событие | Доказанное поведение |
|---|---|
| recv timeout в send_command | Метод возвращает None без исключения (57–60), в том числе если до таймаута получен неполный ответ. Подтверждения исполнения команды со стороны OVA нет; отсутствие исключения нельзя считать доказанным успехом команды. |
| Полный ответ на send_command | Возбуждается ResponseError: команда не должна отвечать (61–63). При вызове через send_auto исключение только записывается в журнал, затем возвращается None (79–83). |
| recv timeout в send_query | Преобразуется в ResponseError с сохранённой причиной socket.timeout (68–73); в ветке '?' send_auto исключение не перехватывается (77–78). |
| Timeout при send | send расположен до try в обоих методах. Внешний send_auto подавит его для команды без '?', но не для запроса. |
| BrokenPipeError / ConnectionResetError / другая ошибка сокета | Нет отдельной обработки. Командная ветка send_auto ловит Exception и журналирует; запросная пропускает наружу. Сокет не помечается неисправным и не пересоздаётся. |
| Первый recv возвращает b'' | arr[-1] вызывает IndexError (49–50), а не осмысленную ошибку закрытия соединения. |
| recv возвращает b'' после неполного непустого ответа | arr не меняется; цикл продолжает recv на закрытом потоке. Если последний байт не NUL, возможен бесконечный быстрый цикл (50–51), несмотря на установленный timeout. |

В нормальном варианте команды без ответа сами занимают около 2 с ожидания на recv. Успешный send означает передачу байтов локальному стеку TCP, а не выполнение команды OVA. Отсутствие ответа на команду и отсутствие управления прибором здесь не различаются.

### 1.4. Жизненный цикл

Hardware/ova5000.py:135–139: __del__ отправляет '*QUIT', ждёт 2 с и закрывает сокет. Нет try/finally; ошибка отправки может не дать дойти до close. Нет явного штатного disconnect/reconnect API, shutdown, прекращения активного чтения или опроса. Назначение '*QUIT' на сервере требует спецификации: нельзя автоматически считать его ни возвратом Local, ни безопасным закрытием только TCP.

## 2. Управление и готовность: доказано исходниками

- В драйвере нет команд Local/Remote, SYSTem:LOCal, SYSTem:REMote, *CLS, *RST, *OPC?, *IDN? и отдельного определения владельца управления. Из служебных команд используются SYST:RDY?, SYST:ERR?, SYST:ERRD?, SYST:SAVJ и '*QUIT'.
- Конструктор не запрашивает ни идентификацию, ни готовность, ни фактический диапазон. Он лишь подключает сокет и устанавливает локальные значения: центр 1550 нм, ширина 2.55 нм (31–44).
- acquire_spectrum (86–101): SCAN → повтор SYST:RDY? до первого символа '1' → SYST:ERR? → при ненулевом первом символе SYST:ERRD? и ScanError → чтение X/Y → received_spectrum.
- Нет проверки готовности ДО SCAN, нет явного захвата удалённого управления после ручного режима, нет общего срока завершения, задержки в цикле готовности или флага отмены.
- Если сервер непрерывно отвечает, но первым символом остаётся не '1', измерение может ждать неограниченно. Таймаут сокета не ограничивает такую последовательность успешных ответов.
- Если сервер на запрос вообще не отвечает, после таймаута возникает ResponseError; это другой сценарий, не тот же бесконечный опрос.
- Сравнивается только первый символ. Строгой проверки формата/типа ответа нет. Формальная готовность по SYST:RDY? также не доказывает право текущего клиента управлять OVA без знания протокола.
- Ошибка SCAN, перехваченная send_auto, не прекращает acquire_spectrum: код всё равно переходит к SYST:RDY?.
- change_range (103–114) сперва обновляет локальные значения, потом посылает CONF:CWL и CONF:RANG. При подавленной ошибке отправки локальное состояние может уже не соответствовать прибору.

## 3. GUI: доказано исходниками

### 3.1. Что считается подключением

- MainWindow.py:125: первоначально self.OSA=None. connect_OSA:591–593 создаёт Luna; 638–641 переносит объект в новый QThread, соединяет received_spectrum с painter и force_OSA_acquire с acquire_spectrum. add_thread:68–86 действительно вызывает moveToThread и thread.start.
- Затем включаются элементы управления, в диапазон подставляются локальные поля драйвера, выводится «Connected with OSA» и немедленно запрашивается первый скан (644–656).
- Сообщение о подключении печатается ДО результата первого скана. Конструктор Luna не содержит протокольного рукопожатия. Проверки ping, getpeername, SO_ERROR, heartbeat, прав управления или текущего Local/Remote нет.
- Критерий devices_ready в PairedRecorder.py:187–188 — только наличие двух объектов, не проверка связи. MainWindow.py:313–318 использует именно этот критерий. Для laser-off также проверяется self.OSA is not None (1141–1142).
- except в connect_OSA:657–659 журналирует исключение и пишет предупреждение, но не откатывает self.OSA, сигналы и доступность элементов. Ошибка асинхронного скана вообще не входит в область этого try.
- Повторное Connect не выполняет явного отключения старого force_OSA_acquire, завершения прежнего потока и закрытия старого драйвера. [ГИПОТЕЗА] При сохранении старого объекта внешними ссылками это оставит нескольких получателей/сокетов. Сам факт дублирующей сессии пользователя не доказан.

### 3.2. Команды при живом TCP, но недоступном управлении

- Кнопка Single вызывает только force_OSA_acquire.emit() (1304–1306), без проверки режима, готовности и занятого измерения.
- В Repeat следующая команда привязана к painter.ReplotEnded (1314–1331). При потере спектра эта цепочка сама по себе не восстанавливает связь. Выключение Repeat разрывает сигнал следующего запуска, но не отменяет уже выполняющийся acquire_spectrum.
- Декоратор pyqtSlotWExceptions (Utils/PyQtUtils.py:9–21) перехватывает исключения самого обёрнутого вызова. Он не является обработчиком исключений асинхронного acquire_spectrum в другом потоке.
- S_print_error у Luna объявлен (ova5000.py:29) и подключён к GUI (MainWindow.py:656), но драйвер ни разу его не испускает. Исключения запросов не превращаются драйвером в понятное состояние «управление потеряно»; GUI не отключает автоматически OSA.
- Прямые вызовы change_range в GUI (278–283, 1308–1312, 1502–1509) и save_binary (1488–1493) не превращаются в постановку в поток только потому, что QObject перенесён через moveToThread. В драйвере нет блокировки транзакции send/recv. [ГИПОТЕЗА] Редактирование диапазона/сохранение во время скана может перемешать обмен или прочитать ответ чужого запроса. Кроме того, такой прямой вызов может блокировать GUI на ожидании ответа.
- Параллельные сценарии также получают ссылку self.OSA: MainWindow.py:882–898, 1026, 1113–1127, 1154, 1363–1366. Полный аудит всех исполнителей и очередей относится к следующему куску, но единого арбитра доступа в показанном драйвере нет.
- Таймер парной записи 600 с существует (PairedRecorder.py:143–164, 269–272; PROJECT_JOURNAL.txt:1652–1655). Это таймер отсутствия результата, не таймаут сокета и не возврат Remote. Показанная обработка потери в Repeat запускает новый запрос через S_start_osa (293–301), а не восстанавливает TCP/управление. Гарантировать отзыв уже выполняющегося скана этим нельзя.

## 4. Неожиданные и запоздалые данные

Далее перечислены условные последствия прочитанного кода, а НЕ доказанные события пользовательской сессии:

1. Пока ScanLoop не вызывает recv, уже пришедшие байты остаются в приёмном буфере TCP ОС; фонового читателя у Luna нет. При следующем send_command этот старый ответ может быть прочитан как неожиданный ответ новой команды и подавлен через send_auto. При send_query он может быть принят за ответ нового запроса.
2. После recv timeout локально накопленная часть сообщения теряется при выходе из recvall. Более поздний хвост может остаться в сокете и попасть в следующий обмен. Таймаут не очищает поток и не закрывает сокет.
3. При склейке нескольких сообщений recvall не отделяет первое; при NUL внутри блока плюс неполном следующем сообщении он продолжает ждать. Возможны неправильная привязка ответа, таймаут и ошибка числового преобразования.
4. После SCAN без ответа драйвер не может отличить принятую команду от проигнорированной. [ГИПОТЕЗА] При последующей формальной готовности возможно чтение прежних/ручных данных вместо нового скана; гарантии семантики SYST:RDY? и FETC требуется проверить по руководству.
5. [ГИПОТЕЗА] Переключение Local меняет владение управлением или поведение локального сервера, не разрывая TCP. Драйвер продолжает использовать прежний сокет, потому что состояние владения у него отсутствует.
6. [ГИПОТЕЗА] Переключение Local закрывает/перезапускает сервер или сеанс. Тогда проявятся необработанные EOF/ошибки сокета. Доказательств сохранности TCP в момент отказа пока нет.

Эти механизмы независимы и могут сочетаться. Выбрать один как первопричину без протокольной документации и записи проблемной сессии нельзя.

## 6. Вывод и степень уверенности

Высокая уверенность в статическом выводе: текущая архитектура отождествляет создание объекта и успешный connect с возможностью управлять OVA. Отдельных состояний транспорта, права управления, занятости и синхронности протокольного потока нет. Отсутствует процедура возвращения в управление после ручного режима. Безусловные дефекты обработки EOF: IndexError при первом пустом recv; бесконечное чтение EOF после непустого незавершённого блока. Отдельно установлено отсутствие выделения первого сообщения/сохранения хвоста и контекста после таймаута; требования к допустимым терминаторам, нескольким сообщениям и уведомлениям должны определяться спецификацией сервера Luna, которой в первом куске не было. Эти два класса выводов нельзя смешивать.

#### 10.1. Что пользователь реально может нажать во время измерения

2. Connect находится на page_hardware, Save и Paired — на page_experiment_flow, laser-off — на page_laser_control (UIs/MainWindowUI.py:239–261,327–354,532–547,654–710). Выключение вкладок приборов их не выключает. Обработчики начала/окончания этих режимов не реализуют общего владельца OSA.

[ГИПОТЕЗА ДЛЯ СЕССИИ] Один recv может забрать чужой ответ, а команда — оказаться между запросами другого измерения. #### 10.2. Watchdog и парная запись: существенное уточнение к куску 1

- Обычный асинхронный OSA-скан блокирует поток OSA, а не поток PairedRecorder, поэтому его QTimer может сработать через заданные 600 с при работающем цикле событий (PairedRecorder.py:143–164,269–272,342–348).
- Но пространственный run блокирует ТОТ ЖЕ поток, где находятся PairedRecorder и его дочерний QTimer. Пока run не вернулся, отложенные данные, start/stop и timeout этого потока не обслуживаются. Таймер не является независимым сторожем пространственного измерения. Аналогично длительная работа других объектов общего потока может задержать обработку.
- При потере OSA либо ошибке scope в Repeat _handle_loss закрывает кортеж, открывает следующий и отправляет ещё один S_start_osa, не отменяя предыдущего (284–301). При зависшем слоте OSA запросы могут накапливаться в очереди; по 600 с ограничено ожидание кортежа, а не работа прибора.
- on_osa_data принимает любой received_spectrum подключённого объекта, если is_running=True, и относит его к текущему кортежу (317–330). Идентификаторов операции/сеанса/поколения, проверки инициатора и защиты от позднего результата нет. Спектр от Single, лазерного или пространственного сценария может быть принят как парный; после Stop → Start поздний ответ старого измерения также не отличим от нового.
- Если пространственный acquire_spectrum испускает received_spectrum в общем с PairedRecorder потоке, стандартный AutoConnection может вызвать on_osa_data непосредственно внутри текущего вызова, а не после окончания run. Следовательно, общий поток не является гарантией изоляции сценариев; отличать прямую доставку такого сигнала от заблокированной очереди внешних событий необходимо.

### 13. Как детектировать Local и возвращаться в Remote без выдуманной команды

Детектор Local может опираться на документированный запрос текущего режима/владельца, документированное серверное уведомление или точный код отказа, который спецификация однозначно относит к Local. Эти механизмы и коды ещё надо установить для фактической версии. Нельзя присвоить LocalMode_Detected по отсутствию ответа, EOF, обычному «not ready», отсутствию received_spectrum или переключению окна. Эти признаки дают Error/ControlUnknown. Свидетельство оператора «в ПО показан Local» можно хранить отдельно как ручное подтверждение, не выдавая за ответ протокольного детектора.

Безопасная логическая последовательность возврата (не инструкция послать сейчас команды):

1. Остановить создание запросов от Repeat/пространственного/лазерного/парного сценариев; пометить активную операцию отменяемой, отделить её поздние данные и сохранить уже имеющиеся результаты.
2. По договору сервера завершить/отменить старую операцию и установить границу синхронного сеанса. Если синхронизация утрачена, нельзя очищать поток наугад и одновременно запускать нового читателя; нужен документированный сброс клиентского сеанса либо новое соединение после вывода старого исполнителя.
3. Сохранить право текущего локального оператора. Выполнить только поддерживаемый фактической версией способ разрешения Remote: явное действие в ПО Luna, команда захвата или новый сеанс — какой именно, определит руководство. Если способ доступен только в ПО Luna, ScanLoop должен сообщить об этом, а не изображать автоматический возврат.
4. Получить положительное подтверждение удалённого владения и состояния прибора документированным способом; отдельно подтвердить готовность/отсутствие ещё идущего ручного скана. При отсутствии наблюдаемого подтверждения не объявлять RemoteControl_Idle.
5. Согласовать актуальный диапазон/нужные ручные результаты. Обновить состояние GUI и разрешить новое измерение только после этих шагов; повтор предыдущего SCAN не должен происходить неявно.

Названия SYST:REM, SYST:LOC, *RST, *CLS, *QUIT и общие команды других SCPI-приборов НЕ подставляются вместо неизвестного договора Luna. Готовность SYST:RDY? сама по себе не доказала владение Remote. Для полностью автоматического детектирования и возврата пока отсутствует необходимое первичное описание интерфейса.

4. **Право и настройки:** владение Remote и допустимость нового измерения положительно подтверждены предусмотренным сервером способом; нет более позднего свидетельства Local/утраты прав. Актуальные настройки после Local согласованы без молчаливой перезаписи ручных значений. При отсутствии такого интерфейса остаётся ControlUnknown, а не эвристический Idle.

Либо операция окончательно признана неуспешной/отменённой, частичные результаты и неизвестный исход сохранения явно учтены, а безопасная граница для новой операции подтверждена отдельно. Неясное сохранение не превращается в «успешный спектр + .bin».
6. **Атомарная публикация:** проверка предиката, освобождение владельца операции и смена состояния выполняются одним исполнителем. Сигнал о результате отправляется с идентификаторами после фиксации исхода. Между проверкой и разрешением следующей команды нельзя вклинить старый Stop/Connect/результат или чужую смену диапазона.

Успешность измерения и возможность снова работать — разные признаки: после определённой ошибки прибора возможно позднее восстановить G_IDLE, не объявляя прошлое измерение успешным. При неизвестном исходе .bin переход к новому измерению требует явного разрешения потери/сохранения частичного результата и проверки безопасного состояния, а не простого таймаута.

**Disconnected означает только завершение клиентского сеанса сокета.** OVA может продолжать измерение, а сервер — сохранение файла. Это не физический аварийный стоп OVA, лазера или механики и не передача прав Local. Состояние приборной операции после разрыва хранится как неизвестное до отдельного подтверждения.

### 16. Архитектурный контракт восстановления

#### 16.1. Границы ответственности

Предлагается один владелец сеанса Luna и одна очередь высокоуровневых операций, а не несколько блокировок вокруг send/recv. Внутри остаются простые раздельно проверяемые части: транспорт байтов; накопительный разбор кадров; разбор ответа конкретной команды; координатор сеанса/операции. Наличие границ не требует отдельного класса или файла на каждый метод.

- **Транспорт:** явные open/close, ограниченные по времени connect/write/read, EOF как отдельный исход, полная отправка команды с учётом частичных send. Исключение записи означает неопределённый объём доставки и не разрешает повтор команды. Финализатор не отправляет протокольных команд и не ждёт сеть; основное освобождение — явное, идемпотентное, в finally.
- **Кадры:** на сеанс выделяется ограниченный накопительный байтовый буфер; выделяется один полный кадр, остаток сохраняется. Разделитель, кодировка, допустимые пустые сообщения и формат массивов определяются профилем подтверждённой версии. NUL пока лишь соглашение текущего кода, не универсальная норма Luna. Нельзя применять strip/игнорирование NUL/ошибок decode для «лечения» потока.
- **Обмен:** не более одного ожидающего ответа, без конвейера запросов. Тип команды и ожидаемость ответа задаются договором, а не наличием символа `?` в строке. Для документированной команды без ответа не выполняется recv «до таймаута ради успеха»; факт отправки не равен принятию/исполнению. Неизвестный ответ на такую команду — ошибка, кроме документированного уведомления.
- **Операция:** один инициатор, поколение сеанса, номер операции, поколение сценария, срок и токен отмены. Нельзя подменять эти клиентские номера идентификатором результата прибора: если Luna не возвращает такой идентификатор, они не доказывают свежесть измерения.
- **Адаптеры ScanLoop:** все пути раздела 10 переходят на арбитр. GUI не ждёт блокировку; пространственный/лазерный сценарии могут ожидать завершение своего запроса только вне GUI, с ограничением срока и проверкой отмены. Никаких прямых обращений к старому объекту OSA в обход очереди, в том числе change_range/save_binary и автоматических повторов.

| Событие | Значение | Обязательное действие |
|---|---|---|
| Таймаут полного ответа send_query, даже если не пришло ни байта | Ответ может прийти позже; без идентификаторов его нельзя связать с новым запросом | Завершить запрос ошибкой, пометить сеанс несинхронным, запретить следующий запрос/SCAN и закрыть старый сеанс. Не продолжать SYST:ERR? на этом потоке |
| Таймаут/ошибка записи, частичная отправка | Команда могла быть принята полностью/частично; факт исполнения неизвестен | Та же изоляция и закрытие; не досылать «новую попытку» SCAN/CONF/SAVJ после ошибки |
| EOF до первого байта либо внутри ответа | Удалённая сторона завершила поток, кадр отсутствует/оборван | Немедленно завершить чтение осмысленной транспортной ошибкой с фазой операции; никаких arr[-1], повторов recv(b'') и числового разбора частичных данных |
| Неожиданный NUL/пустой кадр, неверные байты/кодировка, лишний ответ | Нет доказанного соответствия ожидаемому ответу | По умолчанию ошибка протокола и недоверенный сеанс; не удалять байты и не выдавать успех. Допустимое документированное уведомление обрабатывается отдельно |
| Валидный полный кадр с недопустимой семантикой, например неизвестный статус или несовместимые X/Y | Ошибка данных/протокола; свежесть результата не доказана | Измерение не публиковать как успешное; консервативно Error и новое рукопожатие. Не пытаться поправить данные обрезанием до меньшей длины |
| Полные корректные ответы «0» на SYST:RDY? до общего срока | Транспорт может оставаться синхронным, прибор не завершил работу | Опрос с ненулевой паузой и общим сроком; по сроку прекратить создание запросов, исход измерения неизвестен. Не объявлять desync лишь из-за готовых «0», но закрыть сеанс при выбранной консервативной политике без документированной отмены |
| Документированная ошибка SCAN/SAVJ | Определённый отказ операции, не обязательно потеря TCP или Local | Завершить операцию ошибкой; разрешённое описание ошибки читать только на синхронном потоке. Новый Idle только через G_IDLE |
| Положительное сообщение Local/утраты владения | Право управления потеряно, TCP может быть жив | Запретить новые изменяющие команды, остановить сценарии; активную транзакцию не считать успешной. Сохранение сеанса допустимо лишь при документированно известной границе обмена |
| Только молчание, EOF или обычная ошибка без кода Local | Причина потери управления неизвестна | Error/ControlUnknown, но не LocalMode_Detected; не захватывать Remote по предположению |

Если однозначно распознанное уведомление Local пришло вместе с ответом, оно учитывается до публикации успеха/Idle: наличие данных не отменяет потерю права. Неопознанные соседние кадры не запасаются как «ответы на будущие вопросы».

Повторное соединение восстанавливает транспорт, но само по себе не доказывает ни отмены старого SCAN, ни сброса состояния сервера, ни свежести Matrix A. Не допускается «вычитать всё до тишины», послать пробный SYST:ERR?, SCAN, *CLS/*RST/*QUIT либо искать знакомую цифру в мусоре. Возобновление того же сокета после desync допускается лишь при отдельном документированном механизме синхронизации; пока такого основания нет, выбран новый клиентский сеанс.

#### 16.3. Ограничение времени и отзыв операции

Все сроки измеряются монотонными часами. Задаются раздельно сроки соединения/рукопожатия, записи, полного ответа, полной операции и завершения исполнителя. Срок ответа не продлевается каждым принятым байтом; общий срок операции не продлевается каждым «0», следующим FETC или сохранением. Время ожидания каждого шага ограничено минимумом его собственного и оставшегося общего срока.

Опрос готовности начинается по договору SCAN, затем идёт с заданным интервалом; ожидающий цикл проверяет отмену и срок. Бесконечные «0», бесконечно медленный ответ и поток без разделителя имеют конечные исходы. Лимит размера кадра/числа отсчётов защищает также от исчерпания памяти. Конкретные рабочие значения и пределы массивов нужны из договора/эксплуатационных требований; исходные 2 с и парные 600 с нормативами Luna не являются.

Для будущей реализации предпочтителен один рабочий цикл владельца с неблокирующим сокетом и ограниченным ожиданием готовности: каждая итерация возвращает управление не позднее малого интервала проверки отмены. Задания поступают в потокобезопасную очередь, отмена/остановка выставляет потокобезопасный токен без ожидания обработки Qt-слота. Не создаются дополнительные потоки на каждый recv, запрос или попытку подключения. QTimer в занятом рабочем QThread и QThread.quit сами по себе таким механизмом не являются.

На границе срока сначала проверяются отмена/истечение срока, затем разрешается очередной шаг; приход в сроке `now >= deadline` не возрождает закрытую операцию. Порядок гонки «результат против Stop» фиксируется одним координатором: если результат уже окончательно зафиксирован, Stop не переписывает его; если отмена принята раньше, поздний результат не становится успехом. Короткий внутренний интервал ожидания транспорта до общего срока не равен окончательному таймауту запроса.

#### 16.4. Закрытие и повторное открытие без накопления ресурсов

Последовательность относится и к Disconnect, повторному Connect, закрытию окна, desync и обрыву:

1. Координатор закрывает допуск новых задач, инвалидирует поколение запуска и ожидающие задания/подписки старого сеанса. Каждое принятое задание получает ровно один исход: успех, ошибка или отмена; не начатые задания явно отменяются. Repeat и пространственный retry не создают новые SCAN на отказавшем сеансе.
2. Выставляется токен отмены активного обмена. Сам владелец выходит из ограниченного ожидания, больше не отправляет прикладных команд и переводит исходы в конечные. Даже если завершение SCAN неизвестно, клиентское ожидание не продолжается бесконечно.
3. Владелец в finally делает shutdown при применимости и всегда close, включая отказ connect/рукопожатия/парсера. Ошибка shutdown уже закрытого/неподключённого сокета не должна пропустить close или скрыть первичную причину. Ссылка на старый транспорт обнуляется; его буфер уничтожается, а не переносится в новый сеанс. *QUIT не используется до выяснения его смысла.
4. Получено подтверждение, что исполнитель больше не обращается к старому сокету. При завершении рабочего потока выполняется ограниченное ожидание его окончания вне блокирующего GUI; при сохранении единственного рабочего потока достаточно барьера закрытия его сеанса. Не уничтожать QThread, пока его код работает, не пользоваться terminate и не оставлять «спасательные» фоновые потоки.
5. Только после барьера разрешено создать новый сокет и новое поколение, сбросить приёмный буфер и кэш подтверждённых прав/настроек. Повторные нажатия Connect объединяются в одну текущую попытку или отвергаются как занятость; параллельные connect запрещены.
6. Новый сеанс проходит те же проверки, что первичный: подтверждённый протокол/владение, отсутствие прежнего приборного скана, согласование настроек и ручных данных, весь G_IDLE. Старые результаты не принимаются даже при повторном использовании ОС того же номера дескриптора; объект сеанса и поколение важнее числа fd.

Обещание ограниченного закрытия опирается на отсутствие неограниченных вызовов во всём пути, включая разрешение имени и действия сохранения. Socket timeout не ограничивает обычный getaddrinfo: для установленного локального сервера можно использовать согласованный числовой адрес, иначе требуется отдельно ограниченный механизм разрешения, а не «поток, который бросим при таймауте». Нельзя молча заменить фактическую конечную точку.

Если исполнитель вопреки контракту не подтвердил завершение к сроку, это отдельный отказ остановки: сохранить Error, не открывать второй сеанс и не объявлять Disconnected/Idle. Абсолютную гарантию остановки произвольного зависшего системного/стороннего вызова внутри потока дать нельзя; предлагаемая архитектура исключает такие вызовы из штатного пути, а испытания проверяют ограничение. Истечение join само по себе не освобождает поток/дескриптор.

Базовая безопасная политика: закрытие неисправного сеанса автоматическое, повторное открытие — одна попытка по явному действию оператора, без автоматического захвата Remote и без повторения измерения. Если позднее согласуется автоматический reconnect, он ограничивается числом попыток и общим сроком, отменяемыми интервалами ожидания; он повторяет только разрешённое подключение/рукопожатие, а не SCAN/CONF/SAVJ. Неограниченный backoff и фоновое восстановление против действий локального оператора не являются выбранной политикой.

#### 16.5. Атомарность спектра и Matrix A

Транзакция с обязательным .bin принимается арбитром сразу со всеми параметрами и именем файла: проверка G_IDLE → резервирование владельца → принятие нового SCAN по договору → ожидание именно его завершения → SYST:ERR? → XAXI/MEAS → проверка обоих массивов → SYST:SAVJ → документированная проверка завершения сохранения/ошибки → фиксация единого результата → освобождение владельца. Между шагами не допускаются SCAN, CONF, ручное сохранение или запросы других клиентов ScanLoop.

Точный порядок допустимых запросов и проверок определяется руководством; указанная последовательность расширяет текущую (ova5000.py:91–100,116–130), но не является доказанным протоколом Luna. Нельзя вставлять неизвестную команду подтверждения. Проверяются полный формат кадров, согласованное число X/Y и применимость текущего отрезания 10 отсчётов; недопустимые числа определяются договором, а не исправляются молча.

Гарантия имеет три разных уровня:

- **Внутри ScanLoop:** один арбитр исключает замену Matrix A другим нашим SCAN между чтением спектра и SAVJ. GUI-лямбда S_saveData и позднее сохранение по общему received_spectrum эту гарантию не дают; будущая миграция переносит .bin внутрь операции, а не добавляет второй вызов после сигнала.
- **На сервере/приборе:** если ручной оператор или иной клиент может заменить Matrix A в период транзакции, одного клиентского mutex недостаточно. Нужны документированное исключительное владение на весь интервал либо снимок/идентификатор результата, доступный для чтения и сохранения. Без них нельзя обещать соответствие `.bin` спектру; обязательная связанная операция остаётся недоступной, а вопрос блокирует её спецификацию.
- **На диске:** это не ACID-транзакция и не доказанное атомарное создание пары файлов. SYST:SAVJ сохраняет на стороне, определяемой сервером, а не обязательно на диске клиента. Docstring говорит «нет ответа» и предлагает SYST:ERR?, но не устанавливает момент завершения записи, её долговечность и семантику очереди ошибок. Нулевой код сам по себе не заменяет неизвестный контракт завершения. Локальные временные файлы/переименование не исправят неизвестный исход удалённого SAVJ.

Успех составной операции публикуется только после подтверждения всех обязательных частей. Если спектр получен, а сохранение отказало/оборвалось, массивы можно сохранить как частичный результат с явным статусом и идентификаторами, но не выдавать успешную пару, не закрывать парный кортеж чужим спектром и не запускать следующий автоматический шаг. При отмене после SAVJ файл может уже существовать: неизвестный исход не равен «файла нет»; автоматическая перезапись, удаление или повтор SAVJ запрещены.

Ручной запрос «сохранить последний спектр» после другой операции не может означать сохранение старого Python-массива через SAVJ текущей Matrix A. Он либо явно сохраняет проверенную текущую Matrix A с известной принадлежностью, либо отклоняется как устаревший/неопределённый; новый SCAN ради такого сохранения не выполняется.

### 17. План детерминированных испытаний без оборудования для фазы В

#### 17.1. Испытательная архитектура и достоверность модели

В репозитории уже применяются pytest и unittest.mock: pytest.ini:1–2, tests/test_thorlabs_stages.py:1–5,223–226; tests/conftest.py:108–114 подменяет модули Kinesis. Эти подмены не изолируют Luna TCP. В прочитанном полном списке tests и поиске по тестам не обнаружены готовые тесты Luna/PairedRecorder; журнальное сообщение о прежних мок-проверках не считается наличием нынешней транспортной модели.

План не требует запуска полного GUI или реальных драйверов. Основной набор — pytest с внедряемой фабрикой транспорта, монотонными виртуальными часами, управляемым ожиданием и сборщиком исходов/переходов:

1. **Сценарный транспорт в памяти:** ожидает точную последовательность исходящих байтов; имитирует частичные записи, доставку произвольных фрагментов, таймаут, EOF, reset, ошибки connect/shutdown/close. Неизвестная команда немедленно проваливает тест. События помечены виртуальным временем и барьерами, а не time.sleep.
2. **Состояние фейкового сервера:** поколение клиентского сеанса отдельно от приборного состояния; Remote/Local/неизвестное владение; принятый SCAN, занятость, идентификатор набора X/Y/Matrix A, ошибка и таблица сохранённых файлов. Переподключение не должно автоматически стирать занятую OVA или ручной результат. Ошибки выполнения и обрыв транспорта задаются независимо.
3. **Ответы:** SCAN запускает модель измерения без придуманного подтверждения; SYST:RDY? выдаёт сценарную последовательность 0/1; SYST:ERR? — согласованный код; FETC:XAXI? и FETC:MEAS? — массивы известного набора. Для SAVJ записывается идентификатор Matrix A и исход сохранения; для ошибочного SCAN при необходимости задаётся SYST:ERRD?. Терминаторы и коды — явно именованный тестовый профиль, затем сверяемый с первичным руководством.
4. **Разделение источников истины:** есть синтетические тесты устойчивости и отдельные эталонные примеры из подтверждённой спецификации/имеющейся записи. Тестовый код не вызывает продукционный парсер для построения ожидаемых ответов. Условный кадр `0\\r\\0` или `1\\r\\0` в синтетическом профиле не объявляется настоящим wire-форматом Luna. Положительный тест модели не доказывает совместимость с оборудованием.
5. **Детерминированная конкуренция:** барьеры «команда частично записана», «получен X», «до SAVJ», «до публикации», «старый сеанс закрыт» позволяют поставить Stop/Local/Connect/другого инициатора в точно заданный момент. Проверяются команды и исходы, а не случайный порядок потоков ОС.
6. **Небольшой дополнительный набор локального TCP:** собственный фейковый сервер слушает только 127.0.0.1 на выделенном ОС порту, адрес передаётся тестируемому клиенту явно. Никакого localhost:1, пользовательских настроек или подключения к установленному серверу Luna. Сервер/клиент закрываются в finally, потоки имеют конечное ожидание. Этот набор проверяет адаптер настоящего сокета, но не пытается управлять границами recv через sleep: разбиения строго проверяются транспортом в памяти.

Виртуальные часы продвигаются явно при ожидании; каждое испытание имеет конечный лимит шагов, чтобы ошибка «вечный цикл без ожидания» завершалась провалом, а не зависанием тестового процесса. Интервалы и дедлайны для теста задаются малыми условными величинами и не становятся эксплуатационными настройками прибора. Для Qt-проверок достаточно минимального цикла событий и фейковых отправителей/получателей; сначала устанавливается запрет настоящих сетевых connect и аппаратных фабрик.

#### 17.2. Матрица сценариев и проверяемых исходов

Для каждого сценария проверяются: последовательность команд, поколение/инициатор результата, конечное состояние, число успешных/ошибочных завершений, виртуальное время, предел буфера, отсутствие незакрытых сокетов/незавершённых исполнителей после закрытия.

| № | Сценарий и точка воздействия | Критерий принятия |
|---|---|---|
| Т01 | Штатно: подтверждённый сеанс, SCAN, RDY=0,0,1, ERR=0, длинные X/Y | Один SCAN, опрос с интервалом, правильные массивы/идентификаторы и один конечный успех; Idle только после G_IDLE |
| Т02 | Бесконечные полные «0» на RDY | Выход по общему сроку независимо от успешных отдельных ответов; конечное число опросов, нет активного вращения, повторного SCAN и ложного Local/Idle |
| Т03 | Таймаут RDY/ERR/XAXI/MEAS: до байтов и после фрагмента | Старое поколение закрывается; новый запрос на старом потоке невозможен; частичный массив не становится результатом |
| Т04 | EOF до/при частичной записи SCAN, после полной записи, во время RDY | Один определённый клиентский отказ; возможное приборное исполнение отмечено неизвестным, нет автоматического повторения SCAN |

### 20. Модульные архитектурные контракты

Весь раздел — **проект независимой части решения**, не утверждение о наличии этих классов и не чистовая спецификация неизвестного протокола. Предлагается один `LunaSessionCoordinator`, который одновременно выполняет роль `LunaArbiter`: второй конкурирующий диспетчер не нужен. Границы — транспорт, кадры, профиль команд, координатор и тонкие адаптеры существующих сценариев. Возможное размещение — небольшие модули в Hardware; окончательное разбиение файлов определится Фазой Б. Основная цель — раздельная проверка, а не число файлов.

#### 20.1. LunaTransport — только байты и жизненный цикл

- Конструктор получает фабрику сокета, монотонные часы и механизм ожидания готовности; ничего не подключает. Контракт: `open(endpoint, deadline, cancel)`, `send_all(bytes, deadline, cancel)`, `recv_some(max_bytes, deadline, cancel)`, `close()`. Физически эти действия выполняет только поток владельца; интерфейс может реализовываться пошаговым неблокирующим автоматом. Транспорт не знает SCAN, вопросительных знаков, NUL, UTF-8, массивов и Local.
- Сокет неблокирующий. `open` отслеживает завершение connect и его ошибку; нельзя считать готовность к записи доказательством успешного connect без проверки результата. Ожидание ограничено минимумом срока шага, общей операции и интервала проверки отмены. Разрешение имени не выполняется неограниченно в этом пути: числовой адрес из подтверждённой конфигурации либо отдельно ограниченный механизм, как в §16.4. Нельзя молча заменить endpoint на localhost.
- **«Атомарный sendall» означает отсутствие перемежения байтов разных клиентских команд и полную отправку при успехе**, а не сетевую транзакцию «всё либо ничего» и не обещание одного TCP-пакета. На неблокирующем сокете используется цикл частичных `send` с сохранением смещения; `BlockingIOError` означает ожидание готовности, а не новую команду. Не следует буквально вызывать блокирующий `socket.sendall` и терять контроль отмены. Нулевой прогресс записи трактуется как отказ, не бесконечный цикл.
- Успех записи сообщает только передачу всех байтов локальному стеку. EOF (`recv == b''`), broken pipe, reset, окончательный таймаут и отмена — раздельные типизированные исходы. Ошибка после части или всех байтов содержит фазу и известное число локально переданных байтов, но **не делает вывод о принятии команды прибором**. После неё нет автоматической повторной отправки.
- Абсолютный дедлайн не обновляется при каждом байте/частичном send. Нет выделения потока на запрос, recv или таймаут. Буфер отправки не пересоздаётся на каждом смещении без необходимости.
- `close` идемпотентен; после попытки shutdown обязательно выполняется close, даже при исключении shutdown. Ошибка освобождения сохраняется отдельно от первичной причины; барьер закрытия не объявляется достигнутым при неизвестном освобождении ресурса. Никаких `*QUIT` или иных команд в close/деструкторе. Только подтверждённый конец доступа владельца позволяет открыть следующий сеанс.

#### 20.2. LunaFrameParser — граница сообщения, не граница пакета

- На каждый session_epoch — новый экземпляр. Контракт `feed(bytes)` и `pop_frame()` сохраняет неполный хвост, извлекает полные кадры по одному и не читает сокет. `finish_eof()` различает пустой остаток и оборванный кадр; окончательное решение об ошибке ожидающего запроса принимает координатор. Сброс буфера — только при уничтожении сеанса, не при попытке «вылечить» ответ.
- Параметры профиля: точный разделитель ответа (NUL либо подтверждённый CRLF/LF), разрешённые варианты, кодировка, предел кадра и общий предел накопленных данных. **Нет автоматического угадывания разделителя** по первым байтам и одновременного безусловного принятия NUL/CRLF/LF. CR внутри текущих массивов не становится разделителем кадра только потому, что похож на перевод строки.
- Разделитель может пересекать два `feed`; CR в конце фрагмента при режиме CRLF сохраняется до следующего байта. При явно разрешённых нескольких вариантах профиль задаёт однозначный приоритет; для CRLF и LF нельзя оставлять CR в полезных данных либо выдавать второй пустой кадр. Профиль обязан устранять неоднозначность грамматики, а не прятать её в эвристике парсера.
- Сначала выделяется полный байтовый кадр, затем выполняется строгая проверка UTF-8 для текстового профиля. Разрез многобайтового символа между TCP-чтениями допустим; неполная/неверная кодировка в завершённом кадре — ошибка, не `errors='ignore'`/замена символов. NUL-терминатор удаляется ровно как терминатор; пустой кадр не исчезает молча.
- Лимиты проверяются до неограниченного наращивания памяти; размер очередного чтения также ограничен оставшейся ёмкостью. Ограничиваются незавершённый кадр и суммарный остаток/очередь готовых кадров, чтобы поток коротких сообщений не обходил защиту. Используется накопительный байтовый буфер с курсором поиска/потребления и редким уплотнением, а не конкатенация/повторный поиск с начала на каждом байте.
- Парсер сохраняет соседние кадры, но не назначает их будущим запросам. Координатор разбирает все доступные соседние данные до фиксации исхода: разрешённое уведомление обрабатывается отдельно, необъяснённый кадр/хвост ведёт к desync. Пустой буфер не доказывает, что позднего ответа не будет; синхронность опирается на договор профиля.

#### 20.3. LunaProtocolProfile — применимый договор, без собственного ввода-вывода

Профиль неизменяем на протяжении сеанса. Он описывает кодирование запроса, ожидаемость/число ответов, грамматику полного ответа, допустимые состояния и критерий завершения. Чистые функции форматирования/разбора не получают сокет, Qt-объекты, глобальный OSA или право повторять команду. Смена профиля требует закрытия старого сеанса; транспорт при этом не переписывается.

| Логическая операция | Что есть в нынешнем исходнике | Что обязан определить подтверждённый профиль |
|---|---|---|
| SCAN | `SCAN`, ova5000.py:91 | Формат команды, отсутствие/наличие ответа, доказательство принятия нового скана, допустимость по правам; отправка не равна принятию |
| RDY | `SYST:RDY?`, :92 | Полная грамматика статуса и смысл готовности, интервал опроса, связь завершения с новым сканом; не первый символ строки |
| ERR / ERRD | `SYST:ERR?`, `SYST:ERRD?`, :94–95 | Код и описание, разрешённость чтения, потребление очереди ошибок, отличие ошибки операции от потери прав; запрос ERRD не делается на desync |
| XAXI / MEAS | `FETC:XAXI? mode`, `FETC:MEAS? mode`, :96–99 | Режимы/единицы/грамматика чисел, ограничения количества, согласованность X/Y, связь с результатом; отрезание 10 отсчётов не считается нормой протокола |
| SAVJ | `SYST:SAVJ "path"`, :116–130 | Экранирование и допустимый путь, сторона хранения, судьба существующего имени, момент выбора Matrix A и подтверждение окончания; неизвестный исход не повторяется |
| Диапазон | `CONF:CWL`, `CONF:RANG`, :103–114 | Допустимые параметры и порядок пары команд, подтверждение/чтение настроек, исход частичного применения; локальные поля не меняются на подтверждённые до этого |
| Управление/сеанс | Документированных вызовов возврата в драйвере нет | Доказательство прав, Local/уведомления, исключительность, старый приборный скан после reconnect; нельзя подставить типовую SCPI-команду вместо источника |

Профиль содержит возможности, а не фиктивные методы: неподдерживаемая APEX-функция явно недоступна. Терминаторы команд и ответов различаются и задаются независимо. Сроки/лимиты — конечные параметры с источником обоснования; 2 с/600 с текущего кода не становятся нормами. Положительное доказательство свежести/сохранения может быть отдельным документированным протокольным наблюдением, не обязательно идентификатором, которого у Luna может не быть. Тестовый синтетический профиль никогда не выбирается как рабочий запасной вариант.

#### 20.4. LunaSessionCoordinator — один владелец и согласованные исходы

- Внешний фасад принимает неизменяемые описания операций: `open_session`, `acquire`, `set_range`, `save_current`, `cancel_run`, `close_session`. `acquire` сразу содержит требования к обязательному `.bin`, путь, параметры измерения и снимок метаданных. Возвращается дескриптор запроса, а не массив «когда-нибудь» через общий безымянный сигнал. Сетевые действия в конструкторе/методе submit запрещены.
- Единица сериализации — целая операция, не отдельный send/query: SCAN → подтверждённое завершение → X/Y → обязательный SAVJ → единый исход. Внутри не более одного ожидаемого ответа. Полностью полученные RDY=0 ведут к следующему разрешённому опросу с паузой; окончательный таймаут ответа закрывает допуск на старом сеансе.
- Потокобезопасная очередь имеет конечную ёмкость. Под короткой блокировкой только приём/выдача задания, номера и фиксация состояния; ни сеть, ни файловая запись, ни пользовательский обработчик под ней не выполняются. GUI никогда не ждёт освобождения занятой операции: запрос принят или немедленно отклонён с причиной. Срок включает ожидание в очереди; устаревшее задание не начинает SCAN.
- Для многокадрового сценария вводится **логическое владение запуском**: один run владеет OSA до собственного завершения/отмены, иначе чужая смена диапазона между точками нарушит эксперимент, хотя каждый SCAN отдельно сериализован. Это не mutex, удерживаемый сценарием, и не право владения физическим прибором. Конкурирующий run/ручная изменяющая команда получает «занято» и не копится для неожиданного исполнения после Stop. Очередь нужна для принятых операций владельца и управления жизненным циклом; не все клики обязаны становиться ожидающими сканами.
- `session_epoch` меняется при новой попытке сеанса после барьера закрытия; закрываемое поколение сразу теряет допуск. `run_epoch` выдаётся для каждого нового запуска каждого инициатора; `operation_id` уникален в координаторе. Результат несёт все три номера, инициатора, параметры/метаданные, исход и данные. Токен принадлежит конкретному run/операции, а не общему `is_running`, и не сбрасывается следующим Start. Номер fd не используется как личность сеанса.
- Отмена — потокобезопасный флаг плюс пробуждение/ограниченный интервал ожидания владельца; она не зависит от очереди Qt занятого рабочего потока. Cancel старого run не затрагивает новый. Закрытие/Stop снимает допуск сразу; завершение исполнителя и состояние OVA подтверждаются отдельно. При неизвестном приборном исходе GUI показывает это, а не «прибор остановлен».
- Каждый принятый запрос получает ровно один конечный клиентский исход: успех, определённая ошибка, отмена либо ошибка с неизвестным приборным/файловым исходом. Частичный спектр и неизвестность `.bin` — отдельные поля, не второй успех. Сначала под ответственностью владельца фиксируются исход/поколения/состояние, затем уведомляются потребители. Будущее/дескриптор запроса пробуждается независимо от Qt-доставки, чтобы рабочий сценарий мог ждать без взаимной блокировки.
- При `now >= deadline` сначала применяется истечение срока/уже принятая отмена, потом рассматриваются данные; до фиксации успеха проверяются поколения и доступные уведомления. Stop после зафиксированного успеха его не переписывает. Отложенный получатель всё равно повторяет проверку идентификаторов перед побочным действием.
- **Все** входы в RemoteControl_Idle вызывают один G_IDLE из §15; локальный признак «сокет подключён» или «задание закончено» его не заменяет. Внутри зарезервированной составной операции переход в Idle между X и Y/SAVJ запрещён. Для начала очередной операции G_IDLE проверяется вновь. Его доказательства связаны с поколением и инвалидируются Local, закрытием и изменением подтверждённых условий.
- Qt-мост маршрутизирует `state_changed`, `operation_started`, `operation_finished` через явно очередную доставку в QObject-получатели GUI. Проверка актуальности выполняется **до** адаптации результата в существующий `Painter.set_data(X, [Y], channels)`. Painter не управляет жизненным циклом Luna; его `ReplotEnded` не запускает сетевой запрос. Массивы после публикации не изменяются владельцем; потребитель, которому нужна модификация, создаёт собственную копию. Не надо копировать массив на каждый сигнал без необходимости.
- Закрытие окна асинхронно начинает отмену/закрытие и сохраняет объекты до подтверждения завершения. GUI не делает `wait/join` и не уничтожает работающий QThread. Отказ закрытия не маскируется новым сеансом. Для остальных приборов это не обещание физического аварийного останова; их жизненный цикл не подменяется Luna-координатором.

#### 21.2. Scripts/ScanningProcessOSA.py — управляемое ожидание своего запроса

1. `run` сохраняет последовательность существующего эксперимента (фон, контакт, спектры точки, сопровождение, отвод, перемещение), но получает клиентский фасад и неизменяемый контекст run. Подписка запуска переносится из MainWindow.py:1451 в одноразовую инициализацию. Пространственный исполнитель отделяется от PairedRecorder и обработчиков, которым нужен свободный цикл событий.
2. `_acquire_with_retry` (:102–113) заменяется запросом `acquire` и ожиданием его дескриптора **только в отдельном потоке сценария**. Это асинхронная по отношению к транспорту/GUI операция: координатор работает самостоятельно; сценарий ждёт через условие/событие с конечным сроком и токеном отмены, не через `.result()` без срока и не через вложенный Qt event loop. Пробуждение дескриптора не требует выполнения Qt-слота в ожидающем потоке. Интервальное ожидание не посылает новых запросов и не является retry.
3. Отмена/ошибка прекращает сценарий с одним исходом; нет бесконечного повторного SCAN на том же сеансе. Если локальный срок ожидания истёк раньше доставки исхода, сценарий отзывает именно этот operation_id и ждёт ограниченного подтверждения завершения; он не освобождает OSA и не начинает следующую точку сам.
4. Все точки измерения переводятся вместе: фон (:252), основной цикл (:275), поиск/потеря контакта через прежнюю обёртку (:158,170,195). Дополнительные прямые `acquire_spectrum` после отмены (:180,202) удаляются, а не мигрируют в «обязательный заключительный скан». Проверка отмены стоит после каждого ожидания и перед сохранением, новым движением, настройкой или следующим запросом; отмена не должна приводить к `max(None)` или сопровождению по старому спектру (:287).
5. До измерения фиксируются индекс точки/повтора, фон/основной спектр, координаты и путь сохранения; данные и `.bin` получают один контекст. MainWindow-лямбды :1381–1409 больше не вычисляют принадлежность по положению столика в момент поздней доставки. Для предусмотренных режимов без одной из осей используется тот же явно заданный ноль, что в существующем локальном сохранении, а не разыменование отсутствующего stages/piezo.
6. `SetMode/SetSpan/SetWavelengthResolution/SetCenter` (:129–153,288) не остаются обходом координатора. Требуемые функции проверяются по возможностям выбранного OSA до запуска/движения. Подтверждённое изменение диапазона Luna оформляется через очередь; APEX-специфичные режимы не эмулируются придуманными командами Luna. Неподдерживаемый вариант эксперимента явно отклоняется, а не молча выполняется с другими настройками. Поля `_Span/IsHighRes` заменяются снимком параметров/возможностей.
7. Внешний `try/finally` завершает клиентский run ровно один раз и сообщает причину; освобождение логического владения допустимо лишь после барьера активной OSA-операции. Восстановление настроек после отмены — отдельное безопасно допустимое действие, не безусловный SCAN/CONF на неисправном сеансе. Безопасность механического отвода/физического аварийного останова не доказывается этой отменой OSA.

#### 21.3. Scripts/PairedRecorder.py — собственный поток и адресный результат

- PairedRecorder переносится из общего списка MainWindow.py:146 в отдельный поток с работающим Qt event loop. Координатор Luna имеет свой поток; `_ScopeRetryRunner` остаётся в потоке scope. Пространственный/лазерный сценарий не исполняется в потоке регистратора. Файловая запись не выполняется в GUI или потоке Luna; при медленном сохранении следующий кортеж не стартует до фиксации предыдущего, а ограниченная отмена Luna не зависит от диска.
- Вместо `set_devices(scope, raw_osa)` и глобального `received_spectrum` (:166–178) регистратор получает клиентский фасад и подписку на собственные результаты. У него есть отдельные run_epoch, tuple_id и ожидаемый operation_id. Проверяются инициатор + session_epoch + run_epoch + operation_id + состояние кортежа, а не только `is_running` (:317–328). Чужой Single/пространственный спектр допускается на график при подходящей политике отображения, но никогда не закрывает парный кортеж.
- `S_start_osa → force_OSA_acquire` (MainWindow.py:307) удаляется для Luna. Начало tuple связывается с событием `operation_started` именно принятой OSA-операции, а не с нажатием кнопки или ожиданием в очереди. Чтобы быстрый исход не опередил регистрацию, приём возвращает handle до доставки событий; начальные метаданные/подписка фиксируются до запуска, а started/finished имеют порядок и номера. Scope запускается после принятого начала первого цикла.
- Single по-прежнему требует ровно один собственный OSA и один собственный scope; N:1 Repeat не превращается в фиксированные 5:1. OSA-граница закрывает свой кортеж, завершившиеся scope-измерения относятся к текущему кортежу согласно существующей политике; в коротком промежутке без открытого кортежа допускается pending_scope **только того же run**. Порядок событий при совпадении границы фиксируется в регистраторе.
- Scope-события также должны нести метку запуска запроса, захваченную исполнителем **до** `scope.acquire`, а не текущий run в момент доставки. Прямая подписка регистратора на все `scope.received_data` не даёт этого. Тонкий адаптер scope связывает результат с единственным активным запросом регистратора, запрещает конкурирующий ручной scope-запуск в этот период и не перепривязывается до завершения прежнего вызова. Если драйвер выдаёт только безымянный сигнал, граница его доставки должна быть подтверждена до нового запроса; простое добавление текущего tuple_id в on_scope_data не считается корреляцией. Переписывание протокола scope не входит в Luna-работу.
- Watchdog :162–164,269–271,342–348 остаётся максимум пользовательским контролем срока/доставки: он отправляет cancel конкретного handle, а не открывает новый кортеж и не посылает новый SCAN. Источник конечного сетевого исхода — координатор. Stop (:274–279) прекращает новые запросы, инвалидирует run, собирает уже подтверждённые частичные данные, закрывает кортеж один раз после завершения активных клиентских операций; старый pending_scope не переносится в новый run.
- `_handle_loss` (:293–301) не может безусловно продолжать OSA после её таймаута/Local/desync. Это осознанное безопасное изменение прежней политики «Repeat продолжается при любой ошибке» из PROJECT_JOURNAL.txt:1649–1654: при исправной Luna и изолированной ошибке scope повтор допустим только после определённого завершения предыдущих запросов; при неизвестном исходе Luna автоматическое продолжение запрещено. Ошибка scope не создаёт второй SCAN, пока первый не завершён. Отдельный отказ scope не обязан объявлять TCP Luna неисправным.
- Форматы `osa_1.pkl/.csv`, `scope_k.*`, `times.txt` сохраняются по смыслу, но принадлежность и частичный исход фиксируются явно. Массивы валидируются до сохранения: текущее усечение OSA до `min(len(X),len(Y))` (:118–129) не скрывает ошибку согласованности координатора. Сохранение неполного кортежа не выдаётся за успешную пару.

#### 21.4. Scripts/ScanningProcessLaser.py — два независимых инициатора одного сервиса

Один класс обслуживает два пути, поэтому миграция обязательна для обоих:

| Путь | Точки подключения | Требование |
|---|---|---|
| Обычный лазерный скан | MainWindow.py:882–900,1025–1035,1038–1046 | Передать фасад и отдельный run; дождаться собственного результата до сохранения/следующей настройки лазера; Stop отзывает run вместо одного флага |
| laser-off | MainWindow.py:1110–1129,1151–1168,1171–1176 | Тот же механизм, но другой инициатор/run и поток; режим не трогает лазер, сохраняет постоянную длину волны и имена `S_<номер>_W=...`; без выбранного OSA не захватывает OSA |

Прямой вызов :94–95 заменяется тем же отменяемым ожиданием дескриптора, что у пространственного сценария. Завершение ожидающего run не зависит от Qt-слота в его занятом потоке. После отмены проверка стоит до PM-измерения/перехода к следующему шагу; долгие паузы самого сценария становятся отменяемым ожиданием, чтобы Stop не обходился следующим действием. Это не новое обещание физической остановки/изменение политики включения лазера.

Сопутствующее исправление строго определено: в :102 передавать **`Data` вместо `'Data'`**, где Data построен в :97 из подтверждённых X/Y. Потребитель Logger.py:42–56 не исправляет литерал автоматически; при pickle он может сохранить именно строку. Имена и числовые данные проверяются отдельно для обычного и laser-off режимов. На ошибке/отмене нет фиктивного массива и повторного SCAN. Открытый файл мощности закрывается в finally, S_finished испускается ровно один раз с актуальной принадлежностью запуска; ни старый finished, ни поздний спектр не включает кнопки нового run.

#### 21.5. Порядок чистого перехода и граница совместимости

После разрешения блокеров: сначала изолированные слои/доказанный профиль и адресные тесты; затем координатор/Qt-мост и общий договор клиента; затем **единый согласованный перевод всех пяти путей**, управления диапазоном/Save/Connect/закрытия; после этого удаление сетевого старого пути. Нельзя выпускать промежуточное состояние, где часть клиентов идёт через арбитр, а часть ещё читает тот же сокет напрямую.

Для Luna не остаются публичные обходы через `sock`, `send_auto`, `send_query`, `recvall`, старый `acquire_spectrum`, сетевые лямбды или деструктор с `*QUIT`. Существующий интерфейс Painter — конечный адаптер визуализации, не обратная совместимость с прежним управлением. Одноразовые подписки заменяют многократные connect и широкое отключение чужих подписчиков. Неактивный `force_OSA_acquireAll` из §10 не превращается в новый Luna-канал.

Общие сценарии поддерживают и другие OSA. Их нельзя оставить вызывающими несуществующий новый API: тонкие постоянные адаптеры выбранного прибора предоставляют договор запроса/результата и возможности; они не являются псевдонимами старого Luna-транспорта. Существующие APEX/Yokogawa/Interrogator операции сохраняются в соответствующей ветке; данный план не требует рефакторинга их протоколов и не обещает им Luna-гарантии отмены. Проверки потребителей выполняются фейковыми клиентами, а не подключением других приборов.

### 22. Спецификация устройства MockLunaServer для будущей Фазы В

Это **документированный проект настоящего офлайн-стенда**, а не созданный файл/пустой класс и не запуск сервера сейчас. Используются существующие соглашения pytest/unittest.mock; tests/conftest.py:108–114 подменяет только Kinesis и не запрещает сеть/другие аппаратные импорты. Следовательно, его одного недостаточно для безопасного запуска тестов Luna.

#### 22.1. Общее ядро сценария и два способа доставки

1. **Независимая модель сервера:** состояние прав Local/Remote, занятость прибора, принятый scan_id, наборы X/Y/Matrix A, код/описание ошибки, таблица виртуально сохранённых файлов. Состояние соединения и состояние прибора раздельны: разрыв TCP не стирает текущий скан, чужое владение и сохранённые данные. Внешний ручной скан — действие модели, а не настоящий клиент/прибор.
2. **Сценарный планировщик:** записи «ожидать точные байты команды», «передать фрагмент», «не отвечать», «выдать EOF/reset», «сменить Local/Matrix A», «дождаться именованного барьера». Действия привязаны к номеру команды, точке операции и виртуальному времени. Журнал модели хранит полученные байты, момент принятия SCAN, выбранную для SAVJ матрицу и завершённость записи. Неожиданная команда/лишнее действие — провал теста, не универсальный успешный ответ.
3. **Основной детерминированный канал в памяти:** внедрённые часы и ожидатель обслуживают тот же сценарий без системных сокетов. Только здесь гарантируются точные границы `recv`, частичные `send`, номер fd, ошибка shutdown и точное событие в момент deadline. Ожидатель продвигает время к ближайшему событию/дедлайну; предусмотрены предел шагов и выявление цикла без ожиданий.
4. **MockLunaServer как локальный TCP-адаптер модели:** listener привязывается только к числовому `127.0.0.1` и порту `0`, после bind передаёт фактически выделенный endpoint тестовому клиенту. Один контролируемый поток сервера, конечное ожидание accept/read/write, явные start/stop и барьеры готовности/закрытия; автоматическое освобождение всех принятых сокетов и listener в finally. Несколько последовательных клиентских сеансов используют сохраняющуюся приборную модель; одновременно активный клиентский сеанс ограничен контрактом.
5. TCP-сервер может послать кадр частями, по байту или склеить несколько кадров в один send, **но ОС не обязана сохранить эти границы на recv**. Поэтому локальные интеграционные проверки утверждают итоговые кадры/команды/состояния, а перебор точных разбиений выполняется в памяти. Аналогично TCP-EOF не гарантирует ошибку именно на выбранном клиентском send: буферизация может позволить ему закончиться. Точное место broken pipe/reset при записи задаётся сокетной подменой. Это принципиальное разделение, не пропуск Т04/Т15.
6. В памяти все сроки виртуальные. В локальном TCP-наборе для устойчивости используются барьеры фактического чтения/получения и реальные конечные сроки с запасом, без ожидания точного числа миллисекунд ОС. Нельзя просто ускорить виртуальные часы, пока серверный поток ещё не получил процессор, и назвать случайный таймаут детерминированным. Гонки точно на сроке проверяются каналом в памяти.
7. Команды и эталонные ответы описаны независимыми буквальными байтами синтетического профиля; сервер не строит ожидаемый результат вызовом продукционного парсера/кодировщика. Набор сверки с руководством выделяется отдельно после ответа 9. Модель может знать внутренний scan_id и сохранённую Matrix A, но драйвер узнаёт только то, что реально передано по выбранному профилю. Запрещён скрытый доступ клиента к флагу Local или идентификатору модели ради прохождения теста.

#### 22.3. Контракт безопасного запуска, изоляции и доказательств

- Сейчас **никакие тесты/серверы не запускаются**. В Фазе В выбирается явный список новых изолированных тестов Luna/адаптеров; не `pytest tests` и не обнаружение всех существующих аппаратных диагностик. Существующие файлы tests/conftest.py и pytest.ini учитываются при будущей организации набора, но не выдаются за сетевую песочницу.
- До импорта исследуемых модулей устанавливаются запреты аппаратных фабрик и настоящих сетевых подключений. Одна autouse-фикстура после collection недостаточна против побочного эффекта импорта: изоляционный загрузчик/ранний тестовый модуль должен устанавливать ограничения до импорта драйверов/GUI. Приложение целиком и аппаратные фабрики MainWindow для этих проверок не запускаются.
- Основной набор не создаёт системных сетевых сокетов вообще. В отдельном TCP-наборе разрешены только listener и соединение к **точному endpoint, выданному текущей фикстурой MockLunaServer**. Одного разрешения всего localhost недостаточно: реальное ПО Luna по текущему коду тоже может работать там. Запрещены DNS, другие loopback-порты, wildcard bind, внешний адрес, чтение endpoint из пользовательских настроек и запасной переход к аппаратному драйверу.
- Контроль охватывает connect/connect_ex/create_connection и фабрики backend; не только одну удобную обёртку. Для строгого отсутствия внешней сети тестовый процесс дополнительно запускается в среде, запрещающей внешние сетевые соединения: Python-подмена сама по себе не блокирует нативные библиотеки/подпроцессы. Их запуск не требуется тестам и должен быть запрещён/исключён из импортов. Эти ограничения — требование будущего запуска, не утверждение, что такая среда уже настроена.
- Для Qt достаточно минимального цикла событий и адресных получателей; проверка GUI подтверждает, что обработчик submit/Stop возвращается и событие GUI проходит, пока сервер удерживает ответ. Не требуется открывать полноценное аппаратно подключающееся окно. Числовой ID потока фиксируется фейковым транспортом для проверки единственного владельца.
- Все записи — в временный каталог теста/виртуальную таблицу сервера; не `data/`, не пользовательские `.bin`, не существующие Logs. Модель SAVJ не исполняет переданный путь как произвольный путь ОС. Нет физических приборов, HTTP-запросов и внешних сетевых команд.
